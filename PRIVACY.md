# Privacy

Mushroom Journal keeps your journal on your phone. Nothing is sent anywhere unless
you press the button that sends it, and that button names its destination.

This file describes what is true of the code in this repository *today*. When that
changes, this file changes in the same commit as the code that changed it.

## Today

The app's manifest declares **two permissions**, and only one of them is ever asked for.

`ACCESS_COARSE_LOCATION` is a runtime permission, requested only when you press the
button that uses it — see `app/src/main/AndroidManifest.xml`.

`INTERNET` is not a runtime permission. Android grants it at install and never asks, so
nothing on the phone is going to raise it on the app's behalf and it is said here
instead. It arrived with iNaturalist publishing and is used for nothing else: there is
no background sync, no analytics, no crash reporting and no telemetry. The journal, the
photographs and the region pack are all still on the phone, and stay there unless you
press publish.

One permission does appear in the built APK, and it is worth naming rather than glossing:
`com.wanderwildwood.kinokocho.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`. It is generated by
the Android build tools, it is defined by this app for this app, and it grants no access to
the device or to you — it exists so that the app's own internal broadcasts cannot be
received by other apps. Nothing in this repository asks for it.

## Photographs, and why they cost no permission

The app takes photographs and still declares no CAMERA permission, which is worth
explaining rather than leaving to look like an oversight.

It does not open a camera. It hands one write-once file address to whatever camera app
the phone already has, and gets a picture back. An app that *declares* CAMERA must then
be granted it before the system camera will answer; an app that does not declare it can
do this and never ask for anything. The photograph arrives either way, so the manifest
stays empty.

Pictures are written to the app's own private storage, not the shared Pictures folder,
and are deleted from disk when you delete the find they belong to — which for a while
this file claimed and the code did not do. Throwing away a find you were part-way
through is the one exception, and it is deliberate: the photographs are left alone so
that a mis-tap at the end of a walk costs the record and not the pictures. A photograph
can also be removed on its own, by tapping it twice. (Birding wrote its recordings into
shared `Music/` and every media scanner on the phone picked them up. That mistake is not
being repeated, and where you forage is a worse thing to scatter about a phone than a
bird recording.)

A `FileProvider` is declared for this. It is not a permission — it is the mechanism that
lets exactly one file, once, be written by one other app.

## Location

**Typing the place by hand is the default and asks for nothing.** That has not changed, and
it is still the way to use this app if you would rather it knew nothing.

There is now also a button that fills in roughly where you are, because writing coordinates
out by hand on an e-ink keyboard in a wood is miserable. It asks for permission at the
moment you press it, not at startup, and never if you do not press it.

What it asks for is **`ACCESS_COARSE_LOCATION` only**. Fine location is not declared, so the
app cannot receive a precise fix — this is a property of the manifest, not a promise about
what the code does with a precise fix it is holding. What gets stored is rounded further, to
two decimal places, which is a bit over a kilometre. The journal wants to know which
hillside, not which log.

It reads the position the phone already has rather than requesting a fresh one: no radio is
spun up, and if there is nothing cached it says so instead of waiting.

The position is kept as a position on the entry, and the place you type stays your own
words. It used to be written into those words as well — which was the only place it was
kept at all — and finds recorded before that changed still have it in their text, because
rewriting a note somebody wrote is not a thing this app does.

A place lives in the entry on this phone. It leaves in a message you send yourself, or —
if you publish that find — in what goes to iNaturalist, which is the one case where it
leaves without you addressing it to anybody. See below, and read the part about what
"obscured" does and does not mean.

## iNaturalist

**Publishing is a thing you do, one find at a time, by pressing a button that says it is
public.** There is no sync, nothing runs in the background, nothing is queued and nothing
is uploaded because it was your turn. Closing the app mid-push stops it.

The rules this was to be held to were written in this file before any of it was built,
and all four held:

- A deliberate, per-observation action taken at home. It lives at the bottom of one
  find's own page and nowhere else — not on the journal, not on the question screen.
- Sign-in through the **system browser**, not an in-app WebView, so this app never sees
  an iNaturalist password. It uses OAuth2 with PKCE, which is the flow designed for
  applications that cannot keep a secret.
- **Geoprivacy obscured by default.**
- Said plainly at the point of pressing that this is a publication.

### What is sent

The photographs, the characters you recorded, what you looked at and could not say, the
three characters that would have narrowed it most, your own note, the date, and the
place. Not the app's shortlist — the names it had not ruled out stay on the phone,
because that is this app's opinion and it is not what an identifier is short of.

The observation is posted at **kingdom Fungi and no lower**. That is not modesty for its
own sake: an observation posted with no identification at all lands in a pile that
identifiers filter past, so posting it at kingdom is what puts it in front of somebody
who identifies fungi. The app never suggests a species to iNaturalist.

### Obscured does not mean not sent

This is the part worth reading twice, because the word does not mean what it sounds
like.

When geoprivacy is **obscured**, iNaturalist *is told where the mushroom was*. They
store the true coordinates, and they store the place note you typed. What obscuring
changes is what **the public** sees: a random point inside a cell about twenty
kilometres across, and a place name generated from that rather than the one you wrote.
So "the big oak below the spring" is on their server and not on the page.

When it is **private**, they are still told, and they show nobody at all.

If that is not a trade you want to make, the answer is not to publish the find. This app
cannot make a website forget something it has been sent, and it will not pretend
otherwise.

**There is deliberately no "send no location" option.** An observation with no
coordinates can never become research grade on iNaturalist — their own check tests for a
location before anything else — so it is left out of exports and largely passed over by
the people who might have named it. Blank looks like the careful choice and quietly
wastes the record. Obscured is the careful choice.

### What comes back

Only what the community called it, and only for finds this app published, and only when
you ask. The name is stored with the date it was read, because an identification on
iNaturalist can be revised and a name without a date is a name of unknown age.

It is kept apart from what *you* wrote down under "what it turned out to be". The two are
allowed to disagree.

### Signing out

Signing out drops the token from this phone. It does not reach iNaturalist to revoke
anything, and this file is not going to claim it does — revoking this application's
access is done on iNaturalist, under your account settings.

### Builds without an application id

The iNaturalist application id is not in this repository. A build made without one has no
publishing button at all and cannot reach the network. See the README.

## Keeping a copy

Under the (i) there is "Keep a copy of everything", which writes the whole journal — every
kept find and every photograph — into a zip and hands it to the share sheet. Where it goes
from there is entirely your choice: a cable, a drive, a message to yourself. The app never
sends a backup anywhere itself — the only thing it uploads is a find you pressed publish
on.

The file is written into the app's cache, which the system may clear whenever it likes, and
is handed out one URI at a time through the same `FileProvider` the camera uses. Inside is
plain JSON with the schema's own names, so the notes are readable with a text editor and no
app at all.

It only reads. Nothing in the export can alter the journal, which is the property that
matters in a thing you reach for when something has already gone wrong.

"Read a copy back in" is the other direction, and it only ever adds. A find whose id is
already in your journal is left exactly as it is, so an old copy read onto a phone that
has been used since keeps both. Nothing is deleted and nothing is overwritten. The file
is read through the system picker, which hands this app one file you chose and nothing
else — no storage permission is asked for or held.

## Sending a find to a person

The other way out, and still the first one to reach for: the share sheet takes a find as
plain text and photographs, going wherever you send it. It is one action, per find, and it
names nothing you have not seen — the description, what you looked at and could not say,
and the shortlist of what has not been ruled out. Where it goes after that is between you
and whoever you sent it to. No account, no network permission needed, nothing published.

This carries the shortlist where the iNaturalist text does not. The difference is the
reader: a person you chose can take "not ruled out" as it is meant, and a queue of
strangers reads a list of names as a claim.

## Verifying this yourself

- The source is at this repository, and each release is tagged.
- `grep -r uses-permission app/src/main/AndroidManifest.xml` shows exactly what is asked for.
- Any APK can be checked with `aapt dump permissions` or by opening it as a zip.
- Everything the app can send is built in `app/src/main/kotlin/.../net/`, and the only
  file in this repository that opens a socket is `INatClient.kt`. `grep -rn "URL(" app/src`
  finds it and finds nothing else.
