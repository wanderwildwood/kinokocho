# Privacy

Mushroom Journal keeps your journal on your phone, and it cannot go online: it has no
internet permission. Nothing leaves the phone unless you send it yourself, through the
share sheet or a backup file you save.

This file describes what is true of the code in this repository *today*. When that
changes, this file changes in the same commit as the code that changed it.

## Today

The app's manifest declares **one permission**, and it is asked for only when you press
the button that uses it.

`ACCESS_COARSE_LOCATION` is a runtime permission, requested only when you press the
button that uses it — see `app/src/main/AndroidManifest.xml`.

**There is no `INTERNET` permission**, so Android gives the app no way to reach the
network. The journal, the photographs, the region pack and the key are all on the phone.

Versions up to 0.3.40 carried code for publishing a find to iNaturalist, which worked
only in a build made with an iNaturalist application id. That code is gone. If a phone ever signed in with it, the sign-in it kept (the tokens, the user name and
the location setting) is deleted the first time this version starts. A find such a version
published still has its iNaturalist record (the observation's id there, when it went, and
what the community called it) in the journal and in backups, unchanged; the app no longer
shows or uses it.

One permission does appear in the built APK, and it is worth naming rather than glossing:
`com.wanderwildwood.kinokocho.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`. It is generated by
the Android build tools, it is defined by this app for this app, and it grants no access to
the device or to you — it exists so that the app's own internal broadcasts cannot be
received by other apps. Nothing in this repository asks for it.

## Photographs, and why they cost no permission

The app takes photographs and still declares no CAMERA permission, which is worth
explaining rather than leaving to look like an oversight.

It does not open a camera. It hands one write-once file address to whatever camera app
the phone already has, and gets a picture back. An app that *declares* CAMERA must then
be granted it before the system camera will answer; an app that does not declare it can
do this and never ask for anything. The photograph arrives either way, so the manifest
stays empty.

Pictures are written to the app's own private storage, not the shared Pictures folder,
and are deleted from disk when you delete the find they belong to — which for a while
this file claimed and the code did not do. Throwing away a find you were part-way
through deletes its photographs too: a picture whose find is gone could not be seen
anywhere in the app or go into a backup. Both offer Undo, and nothing leaves the disk
until you start or open another find or leave the app. A photograph
can also be removed on its own, by tapping it twice. (Birding wrote its recordings into
shared `Music/` and every media scanner on the phone picked them up. That mistake is not
being repeated, and where you forage is a worse thing to scatter about a phone than a
bird recording.)

A `FileProvider` is declared for this. It is not a permission — it is the mechanism that
lets exactly one file, once, be written by one other app.

A camera app may write the exact spot a picture was taken into the file, and a picture
picked from the gallery may carry one too. The app takes that out as each photograph comes
in, along with any serial number or owner's name, and checks again before a photograph goes
out in a share or a backup. The date and the camera's settings stay in the file. The place
can also be written as text beside those tags (XMP), and that goes too. A picture in a form
the phone cannot edit, such as HEIC, is saved again as a plain JPEG, which carries nothing
but the picture; one from the gallery that cannot be read at all is not taken in, and a
photograph that cannot be made clean is left out of a share.

## Location

**Typing the place by hand is the default and asks for nothing.** That has not changed, and
it is still the way to use this app if you would rather it knew nothing.

There is now also a button that fills in roughly where you are, because writing coordinates
out by hand on an e-ink keyboard in a wood is miserable. It asks for permission at the
moment you press it, not at startup, and never if you do not press it.

What it asks for is **`ACCESS_COARSE_LOCATION` only**. Fine location is not declared, so the
app cannot receive a precise fix — this is a property of the manifest, not a promise about
what the code does with a precise fix it is holding. What gets stored is rounded further, to
two decimal places, which is a bit over a kilometer. The journal wants to know which
hillside, not which log.

It uses the position the phone already has when that is from the last fifteen minutes. If
not, it asks the phone for one now, from the network or GPS, waits up to about twenty
seconds, and says so if none comes. Either way the answer is only as precise as approximate
location allows, and it is asked for only when you press the button.

The position is kept as a position on the entry, and the place you type stays your own
words. It used to be written into those words as well — which was the only place it was
kept at all — and finds recorded before that changed still have it in their text, because
rewriting a note somebody wrote is not a thing this app does.

A place lives in the entry on this phone. It leaves only in a message you send yourself
or a backup you save.

## Keeping a copy

Under the Backup row beneath the journal title there is "Keep a copy of everything", which writes the whole journal — every
kept find and every photograph — into a zip and opens the system's save screen. Where it goes
from there is entirely your choice: a folder on the phone, a card, a drive app. The app never
sends a backup anywhere itself; it cannot reach the network at all.

The zip is built in the app's cache, copied into the place you picked and then deleted from
the cache. Inside is
plain JSON with the schema's own names, so the notes are readable with a text editor and no
app at all.

It only reads. Nothing in the export can alter the journal, which is the property that
matters in a thing you reach for when something has already gone wrong.

"Read a copy back in" is the other direction, and it only ever adds. A find whose id is
already in your journal is left exactly as it is, so an old copy read onto a phone that
has been used since keeps both. Nothing is deleted and nothing is overwritten. The file
is read through the system picker, which hands this app one file you chose and nothing
else — no storage permission is asked for or held.

## Sending a find to a person

The other way out, and still the first one to reach for: the share sheet takes a find as
plain text and photographs, going wherever you send it. It is one action, per find, and it
names nothing you have not seen — the description, what you looked at and could not say,
and the shortlist of what has not been ruled out. Where it goes after that is between you
and whoever you sent it to. No account, no network permission needed, nothing published.

## The donation link

"Feed the llamas" in About opens a donation page (square.link) in your browser, and only
when you press it. The app hands the browser that one address and nothing else: no find,
no position, nothing about you. If you give, the payment is handled on that page by
Square, not by this app.

## Verifying this yourself

- The source is at this repository, and each release is tagged.
- `grep -r uses-permission app/src/main/AndroidManifest.xml` shows exactly what is asked for.
- Any APK can be checked with `aapt dump permissions` or by opening it as a zip.
- There is no network code at all, and no internet permission in the manifest.
  `grep -rnE "URL\(|Socket|HttpURLConnection" app/src` finds nothing.

## Who we are

Mushroom Journal is made by wander wildwood, an independent developer: one person, not a company. wander wildwood is the data controller for anything the app itself handles, and that is very little. What you put in Mushroom Journal stays on your phone. The app sends nothing out: it has no internet permission. The developer receives nothing, so the developer holds no data about you.

## How to contact us

Write to email@wanderthe.dev about your data, this policy or anything else. The same address is in the app, under About.

## Your rights

If you are in the EU, the EEA or the UK, the GDPR gives you the right to:

- see the personal data held about you (access)
- have it corrected (rectification) or deleted (erasure)
- limit how it is used (restriction)
- object to its use (objection)
- get a copy to take elsewhere (portability)
- withdraw your consent at any time, where something rests on it
- complain to a data protection supervisory authority, for example the one where you live

Similar laws elsewhere, such as the CCPA in California, give you the right to know, delete and correct, and to opt out of the sale or sharing of your data. Nothing from Mushroom Journal is sold or shared.

Since Mushroom Journal keeps what it stores only on your phone, you can exercise most of these rights yourself: edit or delete a find in the app, keep a copy of everything from the Backup row under the journal title, clear the app's data in Android's settings, or uninstall the app, which deletes all of it. For anything you cannot do yourself, write to the address above.
